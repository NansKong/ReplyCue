# Managed beta setup

The static website and managed gateway are separate Vercel projects. Use apps/website for the site and apps/gateway for the Node gateway. The Windows installer reads the same public configuration as the website. Leave the managed settings blank to keep the existing local-key development flow.

1. Create a dedicated Firebase beta project. Enable Email/Password Auth, email enumeration protection and an appropriate password policy. Add the website domain to Firebase Auth and create a Firestore database. Apply apps/gateway/firestore.rules to the dedicated project so only server credentials can access the ledger. Do not replace rules on a shared production database with this file.
2. Configure the gateway project with FIREBASE_SERVICE_ACCOUNT_JSON and a dedicated GROQ_API_KEY as server-only secrets. Use a limited service account that can read Auth users for revocation checks and transact against Firestore. Keep these credentials out of the repository, client config and installer.
3. Set TRIAL_LIMIT_MICROUSD and BETA_LIMIT_MICROUSD as positive integers. The cap is cumulative across the beta. One USD is 1,000,000 microdollars. Configure AUDIO_RESERVE_MICROUSD to cover the provider's maximum billable amount for a 21-second Whisper Turbo request, including rounding. Configure ANSWER_RESERVE_MICROUSD to cover the maximum for a 32,000-byte prompt, provider framing and 2,048 completion tokens for the fixed GPT-OSS model. Verify rates, token accounting and provider minimums before enabling the gateway. These are conservative reservations, so displayed allowance can decline faster than actual provider spend.
4. Start with BETA_ALLOWED_EMAILS as a comma-separated invite list and BETA_ENABLED=false. Configure endpoint-level rate limits in the hosting platform to protect Firebase and hosting spend. Enable BETA_ENABLED=true only after testing with staging credentials and a small cap. Set independent provider-level spending limits where available. The Firestore cap bounds reserved Groq calls through this gateway. It does not cap Firebase, Vercel, requests sent elsewhere or charges above the configured reservation.
5. Set apps/website/public/managed-config.json with the Firebase **web** API key and the fixed HTTPS gateway URL ending in /api/ai. The web key and URL are public configuration. Rebuild the website and Windows installer together, then point the website download button to the managed release asset. Existing v0.1.5 downloads still use the original local-key flow.
6. Before inviting users, verify sign-up, verification email, password reset, sign-in, expiry, disabled/revoked accounts, account changes, concurrent requests near the cap, provider failure and hitting the per-account/global limits. Confirm no upstream request occurs if the transaction is denied or fails. Use separate Firebase data and budgets in staging. Keep preview deployments disabled for paid calls.

The server authorizes verified email accounts and checks token revocation. It reserves against a single Firestore global ledger and an email-based trial ledger in one transaction before calling Groq. Failed or timed-out requests retain the reservation because the provider may have billed them. A new account using the same verified email cannot reset its allowance. Multiple distinct email addresses remain possible, so keep the invite list and total cap during early testing.

The Windows session holds Firebase tokens in memory and clears them at sign-out or app exit. Managed requests have no direct-key or Replicate fallback. The gateway does not persist prompt, audio, or answer content. Users should be told that audio and answer context go to Groq and that coding problem lookups go to the relevant publisher.

Checkout and subscription entitlements are a later step. Keep trial and future paid entitlement decisions on the server.
